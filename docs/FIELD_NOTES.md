# FIELD_NOTES

这份文件记录实际使用中的小技巧、坑点和偏门经验。
它是经验笔记，不是正式支持承诺；请以官方文档、版本行为和实际验证为准。

## 通用

- 适用场景：
  想提高 coding agent 的稳定性、减少返工、把 AI 真正用进日常开发流程。
- 小技巧：
  模型和工具优先选你能长期稳定使用的一套，不要频繁切换主力工作流。需求先聊清楚、约束先写清楚，再把任务交给 coding agent。
- 坑点：
  不要把和 AI 的来回聊天当成项目管理。没有目标、没有约束、没有文档时，结果通常会快速漂移。
- 不要默认不同 agent 的行为模型一样。相同提示词放到 Codex 和 Claude Code 上，执行风格通常不同。

## 模型与付费

- 适用场景：
  在决定主力模型和日常预算时做取舍。
- 小技巧：
  优先考虑官方模型与官方通道，尤其是 `Claude + Claude Code`、`GPT + Codex` 这种一体化体验。贵一点通常能明显降低试错和返工成本。
- 坑点：
  第三方中转或代购虽然能用，但稳定性、合规性、配置复杂度都更高，出问题时往往也更难排查。

## 可沉淀成全局规则的约束

- 适用场景：
  你已经形成了一套稳定工作法，想把它变成 agent 的长期默认行为，尤其适合 `CLAUDE.md`、`AGENTS.md` 这类全局约束文件。
- 小技巧：
  与其原样堆很多条，不如压成少数几组稳定原则：
  - 计划优先：非简单任务默认进入计划模式；遇到问题先停下重规划，不要硬顶；验证步骤也要纳入计划，而不是只管实现。
  - 子代理分工：大量使用子代理做研究、探索、并行分析；一个子代理只做一个任务，避免主上下文变脏。
  - 完成前验证：没证明可行之前不要宣布完成；要看测试、日志、差异行为，并反问自己“工程师会批准这个吗？”
  - 简洁与手术式改动：只改必须改的部分，优先最小实现，不顺手重构，不顺手清理无关代码。
  - 目标驱动执行：把任务改写成可验证目标，复杂任务用 `step -> verify` 的方式推进。
  - 自主修错与复盘：收到 bug、日志、失败测试后直接修；如果项目里有 `tasks/todo.md`、`tasks/lessons.md` 这类机制，就让 agent 持续记录计划、结果和教训。
- 坑点：
  这类规则最容易失控的地方有两个：
  - 写成大段口号，实际不会改变 agent 行为。
  - 把某个项目专用流程硬塞成全局规则，比如默认依赖 `tasks/todo.md`、`tasks/lessons.md`，但很多仓库根本没有这套结构。
  更稳妥的方式是：把“原则”写成全局，把“文件路径和落地动作”留给具体项目再覆盖。

## 多智能体与多 CLI

- 适用场景：
  一个 agent 不够用，或者你想让不同 agent 分工协作时。
- 小技巧：
  让多个 agent 共用同一份需求文档或任务文档，避免每个 agent 各自理解一遍。你最熟的 CLI 可以当主控，让它去调用或协调其他 CLI。
- 坑点：
  多 agent 协作考验的不是“提示词技巧”，而是项目管理能力：任务拆分、资源分配、进度控制、结果验收。

## 文档优先

- 适用场景：
  任何稍微复杂一点、会持续迭代、或者要交接的任务。
- 小技巧：
  把文档当成唯一真源。需求、计划、关键决策、变更结果都要落文档；每次改完东西都可以顺手要求 agent 更新文档。
- 坑点：
  你记不住，AI 更记不住。没有文档时，后续任何“为什么这样做”“现在做到哪了”都会重新消耗上下文。

## 调试与验证

- 适用场景：
  功能已经做出来，但还需要验证、调 UI、修交互或排查奇怪行为时。
- 小技巧：
  让 agent 自己调用测试工具、浏览器工具、截图工具去验证。做完东西之后，可以让 agent 自己截图检查验收；如果有 UI 稿，也可以让 AI 按界面逐个截图走查 UI。
- 坑点：
  不要只问“你觉得改好了吗”。让 agent 用测试、日志、截图、页面行为去证明它真的改好了。

## 长任务与提交流程

- 适用场景：
  复杂任务、长任务、准备提测、准备提交、准备合并之前。
- 小技巧：
  到要提交的时候，最好再起一个空上下文的新 agent 做独立检查。让这个新 agent 只看当前结果、文档和目标，不继承前面的思路惯性；如果发现问题，就让 agent 之间先讨论和复核，实在搞不定再问人类。
- 坑点：
  同一个长上下文里的主 agent 容易对自己的实现路径产生惯性，越到后面越可能“看不出问题”。提交前没有独立检查，容易把错漏直接带进 PR。

## 工具补充

- 适用场景：
  需要把更多外部系统接进 agent 工作流时。
- 小技巧：
  `opencli` 适合把网站、浏览器会话、本地工具转成更稳定的 CLI 界面；`chrome-devtools-mcp` 适合让 AI 用浏览器自己调试；`gh` 适合把 GitHub 操作交给 agent；飞书 CLI 或飞书 API 则适合把文档、知识库、协作系统纳入自动化。
- 坑点：
  工具接得越多，配置漂移和权限问题越容易出现。接入前先想清楚这条链路是不是会被你长期复用。

## 持续学习

- 适用场景：
  想减少重复踩坑，及时知道更成熟的替代方案。
- 小技巧：
  持续关注工具作者、研究者、产品团队和高质量实践者。很多你正在手动解决的问题，可能已经有现成方案。
- 坑点：
  只看热闹不沉淀没用。看到有价值的经验后，最好尽快写回你自己的规则、模板或文档。

## 最后一句

- 适用场景：
  遇到不确定、卡住、不会拆、不会调的时候。
- 小技巧：
  遇事不决先问 AI，但别只问“怎么办”，要尽量带上目标、约束、上下文和你已经试过的东西。
- 坑点：
  AI 可以帮你加速，但不会自动替你定义问题。问题没定义好，换再多模型也只是更快地偏离目标。
