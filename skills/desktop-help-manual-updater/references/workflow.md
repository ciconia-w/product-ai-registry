# 详细工作流

## 1. 收集输入

先识别以下对象：

1. 当前手册源文件（如存在）
2. 项目手册规范文件
3. 正在运行的应用窗口
4. 历史手册、发行说明、产品更新说明或内置帮助资源

## 2. 先判断路线，再做文档计划

先根据 `references/decision-guide.md` 判断当前任务应走：

- 增量更新
- 大幅重写
- 从零编写

如果无法可靠判断，就向人类确认。

如果路线是“增量更新”或“大幅重写”，在深入探索应用前，先根据现有资料建立文档计划或差异计划，把章节、主题或模块分成：

- 大概率可复用
- 必须重新核验
- 明显过时或缺失

旧手册或其它历史资料只能作为覆盖范围清单和写作参考，不能当作当前行为证明。

差异计划可使用：

- `references/templates.md` 中的“差异更新计划”

如果路线是“从零编写”，则不要勉强构造差异计划，而是先建立手册大纲和覆盖清单。模板可使用：

- `references/templates.md` 中的“从零编写手册大纲”

## 3. 建立功能核验矩阵

在正式写文档前，建立轻量矩阵，至少记录：

- 模块
- 场景
- 需要覆盖的状态
- 当前状态
- 截图目标
- 证据或备注

模板见：

- `references/templates.md`

## 4. 按实际产品准备演示数据

在进入内容型流程前，先准备合法、真实感足够的演示数据。

优先考虑：

- 会议纪要
- 制度或规则说明
- 中英双语短文本
- Markdown、TXT、PDF 等常见文档
- 真实感较强但虚构的人名、日期、角色、组织名

不同应用需要的数据类型往往不同，这里不要机械套用固定脚本或固定素材。

如果应用会把历史记录、会话、导入内容或任务结果存到本地：

1. 先观察真实格式
2. 再生成与之相符的演示数据
3. 避免用不符合产品语境的测试垃圾数据污染截图和文档

## 5. 串行探索应用

在同一个真实应用窗口里，所有 UI 操作都必须串行进行：

1. 点击或输入
2. 等待界面变化
3. 检查当前状态
4. 截图
5. 记录结果

不要在同一窗口内并行推进多个点击流。

## 6. 核验完整流程，不只看页面是否打开

不要把“页面能打开”当作验证完成。

对每个重要功能，尽量覆盖以下适用状态：

- 空状态
- 常规状态
- 运行中状态
- 完成状态
- 下拉菜单
- 对话框
- 筛选器
- 开关开/关
- 新增、删除、管理态
- 导出、下载结果
- 历史记录持久化

对于内容型流程，只有满足以下条件才算核验通过：

1. 确实提交了接近真实用户的输入
2. 应用确实对输入进行了可见处理
3. 返回了结果，或返回了明确错误

## 7. 使用接近真实用户的输入

避免使用机械、突兀、明显是测试脚本生成的提示词或样例文本。

如果桌面输入法、粘贴或快捷键不稳定：

1. 先把输入内容写入本地文本文件
2. 尽量使用复制粘贴或较短输入
3. 如产品自带示例卡片、模板或演示入口，优先使用

## 8. 截图后立即复核

每次截图后都要立刻检查：

1. 是否截到了目标状态
2. 文字是否清晰可读
3. 是否混入无关窗口、悬浮层或遮挡
4. 文件名是否能回溯到对应章节或场景

不合格截图要立即重截，不要留到最后统一返工。

如需在当前设备上执行真实截图，优先加载：

- `references/local-screenshot-playbook.md`

## 9. 闭环验证导出与下载

如果某个功能支持导出、下载或生成文件，至少验证：

1. 导出入口能打开
2. 已实际选择具体格式
3. 如有保存过程，已出现对应保存状态
4. 最终目标文件确实落盘并能在磁盘上找到

没有确认最终输出文件存在前，不要把“支持导出”写进手册。

## 10. 根据环境选择合适的操作方式

优先使用当前环境中最稳定、最可复核的方式完成桌面探索。

如果具备可靠的桌面自动化、截图、窗口切换能力：

1. 使用工具完成页面探索、截图和记录
2. 每一步都保留可回溯证据
3. 当前设备已验证可用的截图方式见 `references/local-screenshot-playbook.md`

如果不具备可靠的桌面自动化能力：

1. 改为人工串行操作
2. 每完成一个场景就记录观察结果
3. 必要时以人工截图、人工核对和人工文件落盘验证补齐证据

无论使用哪种方式，都要保证流程可复核，而不是仅凭推测补文档。

## 11. 编写或更新手册

尽量保持原有标题层级，除非确实缺少必要章节。

优先顺序如下：

1. 项目真实手册规范
2. 当前项目已有手册的稳定写法
3. 如果是从零编写，使用 `references/from-scratch-manual-spec.md`
4. 如果是更新或重写，使用 `references/manual-style-template.md` 中的通用回退规范

在最终输出中，清理以下内容：

- 临时编辑器生成的图片路径
- 失效的旧截图引用
- 从历史手册机械复制但已不准确的控件名称
- 与当前项目不匹配的跨项目语法或资源路径

## 12. 输出路径与交付

默认把交付产物输出到“对应系统的非系统盘根目录 `output` 文件夹”下，并在其中创建与产品相关的子目录。

推荐路径示例：

- Windows: `D:\output\<产品名>\`
- Linux: `/mnt/<data-disk>/output/<产品名>/` 或 `/media/$USER/<data-disk>/output/<产品名>/`
- macOS: `/Volumes/<DataDisk>/output/<产品名>/`

执行规则：

1. 优先选择第一个可写、且能明确判断为非系统盘的卷
2. 不要默认把最终交付物写到系统盘根目录
3. 如果系统上不存在可可靠识别的非系统盘，或者没有写权限，就向人类确认输出位置
4. 如果产物由多个文件组成，至少输出入口文件、截图目录，以及必要的样例文件目录
5. 交付时必须给用户一个最短可打开路径

关于“最短可打开路径”：

1. 如果手册是单文件或有明确入口文件，优先给入口文件路径
2. 如果目录更容易整体查看，同时给出输出目录路径
3. 不要只说“已输出到 output 目录”，要给出用户可直接打开的具体路径

## 常见风险

避免以下错误：

1. 把部分验证误判为完整验证
2. 在同一应用窗口里并发操作多个流程
3. 让输入法、剪贴板或乱码污染测试内容
4. 涉及联网功能时忽略代理、登录态或网络环境
5. 在未确认输出文件落盘前就写“支持导出”
6. 把其它项目的文档风格、目录结构或资源路径直接套到当前项目

## 完成前检查

宣布完成前，至少交叉检查以下内容：

1. 当前手册
2. 差异更新计划
3. 功能核验矩阵
4. 已探索到的真实界面状态
5. 已保存的截图和导出文件
6. 最终输出目录与入口文件路径

不应存在未处理、未归类或未说明原因的功能桶。
